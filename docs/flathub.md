# Flathub

> **Status:** DBine isn't on Flathub. The submission was declined, so the
> workflow's "Pull request on Flathub" step is turned off (`if: false && …`
> in `.github/workflows/flathub.yml`). Everything else still runs: the
> manifest is rendered and linted, and the downloadable `.flatpak` bundles
> are attached to every release. The rest of this page describes the setup
> for a future submission.

DBine is published on Flathub as `io.addlayer.dbine`. Flathub builds the app
on its own infrastructure from a manifest kept in
[flathub/io.addlayer.dbine](https://github.com/flathub/io.addlayer.dbine).
This repository holds the template of that manifest and a workflow that
prepares it for each release. The owner's first-submission checklist is in
[`flatpak/README.md`](../flatpak/README.md).

## Files

| File | What it is |
|---|---|
| `flatpak/io.addlayer.dbine.yml` | The manifest template (`@TAG@`, `@COMMIT@`, the cloud client IDs). |
| `flatpak/io.addlayer.dbine.metainfo.xml` | AppStream metadata. `<releases>` is filled from `CHANGELOG.md` when rendering. |
| `flatpak/io.addlayer.dbine.desktop` | The desktop entry (`Categories=Development;Database;`). |
| `flatpak/flathub.json` | Flathub's build settings (architectures). |
| `flatpak/render.py` | Renders the manifest and the metainfo for one tag. |
| `.github/workflows/flathub.yml` | Renders, generates the offline sources, lints, opens the PR on Flathub and builds the downloadable `.flatpak` bundles. |

## The build

- **Runtime:** `org.gnome.Platform` / `org.gnome.Sdk` 51, which ship
  WebKitGTK 4.1 (`webkit2gtk-4.1`). SDK extensions: `rust-stable`, `node24`
  and `llvm22` (libclang, for the Kerberos bindings' bindgen).
- **Offline:** Flathub builds without network. The app comes from a `git`
  source at the release tag and commit; the crates from `cargo-sources.json`
  (flatpak-cargo-generator over `Cargo.lock`) and the npm packages from
  `node-sources.json` (flatpak-node-generator over `web/package-lock.json`),
  both generated by the workflow with flatpak-builder-tools pinned to one
  commit.
- **Commands:** `npm ci --offline` and `vite build` in `web/`, then
  `cargo build --release -p dbine --features flatpak,tauri/custom-protocol`.
  No `plugins` feature: every driver is built into the app and none is
  downloaded. `tauri/custom-protocol` is what `cargo tauri build` adds so
  the app serves the built UI instead of the dev server.
- **Installed:** `/app/bin/dbine`, the desktop entry, the metainfo and the
  hicolor icons at 128, 256 and 512 px (`src-tauri/icons`).

### Modules besides the app

| Module | Why |
|---|---|
| `git` (2.56, from source, without Rust/Perl/Tcl) | Projects and the script library run `git`; the GNOME Platform doesn't have it (only the Sdk does). |
| `unixodbc` | The ODBC driver loads the driver manager (`libodbc.so.2`) at run time; the runtime has none. |
| `libduckdb` | DuckDB's official library, same version and SHA-256 as `crates/drivers/duckdb/src/loader.rs`. |
| `llama-cpp` | llama.cpp's `llama-server` for the AI assistant's built-in model, built from source at the tag `embedded.rs` pins (`ENGINE_TAG`). |

## The Flatpak build mode

The cargo feature `flatpak` (in `src-tauri/Cargo.toml`) is the switch. A
feature rather than an environment variable: it is visible in `Cargo.toml`,
`cargo check --features flatpak` covers it, and Cargo rebuilds when it
changes. What it changes:

- **Updates:** `check_for_update` answers at once with `reason: "flatpak"`,
  without asking GitHub or the updater manifest, so there is no startup
  check and no update notice. A manual check (Settings, or the Help menu
  where there is one) says that Flatpak updates the app.
- **Azure firewall:** the sandbox can't run the system's `az`, so
  **Add my IP** reports `az: "sandboxed"` and the dialog explains why and
  offers the portal, the T-SQL and the command to run in a terminal.
- **Scheduled tasks:** the sandbox has no access to systemd or cron. Saving
  a task works; registering it with the OS scheduler returns a clear message
  instead, and the task can be run from DBine.

Everything else behaves as in the other Linux builds.

### Native libraries: bundled, not downloaded

Elsewhere DuckDB and llama.cpp are downloaded on first use. In the Flatpak
they are modules of the manifest, and two environment variables in
`finish-args` point the app at them; the app already honors both:

- `DBINE_DUCKDB_LIB=/app/lib/libduckdb.so`: the DuckDB driver loads it
  instead of downloading.
- `DBINE_LLAMA_DIR=/app/lib/llama.cpp`: the AI assistant runs that
  `llama-server` and never downloads the engine. The models themselves
  (Qwen2.5-Coder) are still downloaded when the user picks one: they are
  data, not code.

Bundling keeps both features working with no download of executable code
at run time. DuckDB uses its official prebuilt library (building it from
source adds a long C++ build for no gain); llama.cpp is built from source
because its CPU backends are built per instruction set and Flathub prefers
sources.

## Permissions

| Permission | Why |
|---|---|
| `--share=network` | Database servers, cloud sync, the local MCP server on 127.0.0.1. |
| `--share=ipc`, `--socket=wayland`, `--socket=fallback-x11`, `--device=dri` | The window and WebKitGTK's GPU rendering. |
| `--talk-name=org.freedesktop.secrets` | The keychain item (Secret Service) with the key that encrypts saved passwords. |
| `--socket=ssh-auth` | SSH tunnels and git remotes can authenticate with the user's SSH agent. |
| `--filesystem=home` | File databases (SQLite, DuckDB, libSQL) write journal and WAL files next to the database, which the document portal can't provide (it exposes the chosen file alone). Also `~/.ssh` (tunnel keys, `known_hosts`), git projects and the script library, and the other tools' settings files that connection import reads. |

File dialogs go through the file chooser portal. Desktop notifications are
not requested: the only OS notifications DBine sends come from scheduled
tasks run by the system scheduler, which the Flatpak can't use.
`--filesystem=home` and `--socket=ssh-auth` need an exception from Flathub's
reviewers (the linter reports them until it is granted).

## Limits inside the sandbox

- **Azure CLI, Claude Code and Codex CLIs:** programs installed on the host
  can't be run. Azure's firewall rule is created from the portal, T-SQL or a
  terminal; the AI assistant uses the built-in model, Ollama or LM Studio.
- **Scheduled tasks** are saved but not registered with systemd or cron.
- **ODBC presets** need the vendor's driver where the sandbox can read it
  (under the home folder) and registered in `~/.odbcinst.ini`.
- **Files outside the home folder** (other disks, `/mnt`, `/media`) open
  through the file chooser, one file at a time; a SQLite database there may
  not be able to write its journal.
- **Cloud sync with Google Drive and OneDrive** needs the client IDs in the
  manifest (repository variables, see the workflow). Without them the build
  behaves like any build without client IDs ([`sync.md`](sync.md)): Google
  Drive and OneDrive aren't configured, folder sync works.

## Identifier and data

The Flatpak's id is `io.addlayer.dbine`. The data lives under
`~/.var/app/io.addlayer.dbine/` (config, data and cache), separate from a
`.deb`, `.rpm` or AppImage install on the same machine. The single-instance
D-Bus name is derived from the Tauri identifier; Flatpak lets the app own
names under its own id, so the Flatpak release has to carry the identifier
`io.addlayer.dbine` (being renamed on its own branch) for a second launch to
open a window in the running app.

## The workflow

`.github/workflows/flathub.yml` runs:

- when a release is published with a personal token, and after the
  `release` workflow ends well on a `v*` tag (a release it publishes uses
  `GITHUB_TOKEN`, which starts no other workflow);
- by hand, with a tag and `dry_run` (on by default).

It checks out the tag, generates `cargo-sources.json` and
`node-sources.json`, renders the manifest and the metainfo
(`flatpak/render.py`), runs Flathub's linter and `appstreamcli validate`,
and uploads everything as an artifact. Without `dry_run`, it pushes a
`release-vX.Y.Z` branch to `flathub/io.addlayer.dbine` and opens a PR there
with the secret `FLATHUB_TOKEN`; without the secret it skips the PR with a
notice.

## Downloadable .flatpak

Flathub hasn't accepted DBine for now, so every GitHub release also carries
the Flatpak as a single file: `dbine-X.Y.Z-x86_64.flatpak` and
`dbine-X.Y.Z-aarch64.flatpak`. It is the same app as the Flathub build (same
manifest, same permissions, same Flatpak mode).

### How it's built

The `bundle` job of `.github/workflows/flathub.yml`, after `manifest`:

- One job per architecture: `x86_64` on `ubuntu-latest`, `aarch64` on
  `ubuntu-24.04-arm`, both inside
  `ghcr.io/flathub-infra/flatpak-github-actions:gnome-51` (GNOME 51's Sdk
  preinstalled, `--privileged` for flatpak-builder's sandbox).
- It downloads the files `manifest` rendered (the `flathub-vX.Y.Z`
  artifact) and builds them with the official
  `flatpak/flatpak-github-actions/flatpak-builder` action (v6.8, pinned by
  commit), which then runs `flatpak build-bundle` with
  `--runtime-repo=https://dl.flathub.org/repo/flathub.flatpakrepo`. The
  bundle's branch is `stable`.
- The action caches flatpak-builder's state directory (downloads, ccache
  and finished modules): git, unixODBC and llama.cpp are reused from the
  previous release while they don't change; the app always builds from its
  tag. A run takes long (Rust with every driver, inside flatpak-builder).
- The bundle is kept as an artifact (`flatpak-vX.Y.Z-<arch>`). On a real run
  (not `dry_run`), `bundle-release` uploads the bundles that were built to
  the tag's release with `gh release upload --clobber`; it is the only job
  with `contents: write`.
- The bundle jobs are separate from `manifest`: a failed bundle doesn't
  affect the release or the Flathub PR. They run even if the lint or the PR
  failed, as long as the files were rendered. If one architecture fails,
  the other is still uploaded, with a warning.

The `release` workflow's downloads list mentions the `.flatpak`; the files
appear on the release a while after the others, when this workflow ends.

To try it without publishing: Actions › flathub › Run workflow with the tag
and `dry_run` on, or

```sh
gh workflow run flathub.yml -f tag=vX.Y.Z -f dry_run=true
```

### Installing it

```sh
flatpak install --user ./dbine-X.Y.Z-x86_64.flatpak
flatpak run io.addlayer.dbine
```

(`aarch64` on ARM.) The bundle points at Flathub for its runtime: the
install adds the `flathub` remote for the user if it's missing and pulls
GNOME 51 from it (Flatpak shows "Configuring https://dl.flathub.org/repo/
as new remote 'flathub'" and the permissions, and asks before installing). After that DBine is in the applications menu like any
other app, with its data under `~/.var/app/io.addlayer.dbine/`.

### Updates

The bundle doesn't update itself, and neither does Flatpak:

- It is built with the `flatpak` feature, so the in-app updater is off:
  DBine never checks for or downloads a new version, shows no update
  notice, and a manual check (Settings) answers that Flatpak updates the
  app (`reason: "flatpak"` in `check_for_update`).
- But a bundle has no repository to update from: the app's remote is a
  local `dbine-origin` with no URL, so `flatpak update` updates the GNOME
  runtime from Flathub and says nothing about DBine.

To update, download the new version's `.flatpak` from the release and run
the same `flatpak install --user ./dbine-X.Y.Z-<arch>.flatpak`: it replaces
the installed version in place (checked with Flatpak 1.18). The data in
`~/.var/app/io.addlayer.dbine/` is kept; only
`flatpak uninstall --delete-data` removes it.

## Building locally

In a Linux machine or container with `flatpak` and `flatpak-builder` (in
Docker it needs `--privileged`):

```sh
flatpak remote-add --if-not-exists flathub https://dl.flathub.org/repo/flathub.flatpakrepo
flatpak install flathub org.gnome.Sdk//51 org.gnome.Platform//51 \
  org.freedesktop.Sdk.Extension.rust-stable//26.08 \
  org.freedesktop.Sdk.Extension.node24//26.08 \
  org.freedesktop.Sdk.Extension.llvm22//26.08
python3 flatpak/render.py --tag vX.Y.Z --commit <sha> --out build-flatpak
# generate build-flatpak/cargo-sources.json and node-sources.json as the workflow does
flatpak-builder --force-clean --repo=repo app build-flatpak/io.addlayer.dbine.yml
```

To build the working tree instead of a tag, replace the `git` source of
the `dbine` module with `type: dir` and `path: <checkout>` (skipping
`target`, `web/node_modules` and `web/dist`).
