# Document the database

Generates a database's **data dictionary** in a single file: tables,
columns, keys, indexes, views, routines, triggers and, in HTML, an
entity-relationship diagram. It's useful for handing over, versioning or
printing the documentation without building it by hand.

## Where it is

Right-click a **database** in the explorer › **Document the database…**. It
also exists as a step of a [scheduled task](scheduled-tasks.md#document-the-database),
to regenerate the documentation every night.

## The dialog

- **Format:**
  - **HTML:** a single file with index, search, light or dark theme and the
    diagram. It can be printed as PDF from the browser.
  - **Markdown:** text for a repository or a wiki. It has no diagram.
- **Schemas:** those you want to document; empty means **All schemas**. It
  appears only on engines with schemas.
- **Include:** tables; views; procedures and functions; triggers; sequences,
  types and other objects; the source code of views, routines and triggers;
  indexes; foreign keys; dependencies ("Used by"); and the diagram.
- **File:** where to save. If the name doesn't have the format's extension
  (`.html` or `.md`), it is added.

Parts the database doesn't have, or that the engine doesn't offer, appear
disabled with **This engine doesn't have it**.

**Generate** closes the dialog and runs as a background task, with progress
per phase (list of objects, tables, columns and keys, code, writing) and an
option to cancel. When it finishes it shows the number of tables and objects,
and a notification with **Open** and **Show in folder**, which only work with
files generated by this run of DBine. Notes about what couldn't be read go to
the task log.

## What the document contains

- **Header:** the database, the connection, the engine and its version, and
  when it was generated.
- **Per table:** columns (type, nullable, default, key, auto-increment,
  comment), primary key, foreign keys with their on-delete and on-update
  actions, indexes, `CHECK` constraints and triggers.
- **Rows (approximate):** below each table, the number of rows the engine
  already has recorded in its **statistics**. A `COUNT` is never run: it
  doesn't scan or lock the table. The number may be out of date until the
  engine refreshes its statistics (`ANALYZE` and equivalents, depending on
  the engine). If the engine keeps no statistics for that table, the line
  doesn't appear. Which source each engine uses is in
  [`engine-support.md`](engine-support.md#approximate-rows-and-comments).
- **Object comments:** views, procedures, functions, triggers, sequences and
  types show the comment they have in the engine (those of tables and columns
  were already shown).
- **Used by:** what depends on the table. It joins the foreign keys the
  catalog reads with the views, routines and triggers whose code names the
  table. When the name appears inside a text and it can't be certain, it is
  marked **mentions it inside a text: review**.
- **Views, routines, triggers and other objects**, grouped by type in the
  engine's order, with their code if requested.
- **Diagram (HTML):** layered SVG, with the referenced tables on the left.
  Each box shows up to 12 columns and links to its table. Past **150 tables**
  a diagram per schema is built; a schema exceeding that maximum is left
  without a diagram, with a notice in the document.
- **Notes:** what couldn't be read (for example, the code of some object) is
  written at the end, not silently lost.

All names, comments and code are escaped: a comment with `<b>` appears as
text, not as HTML.

The document's language is the interface's; if the scheduled task doesn't
send its texts, it comes out in Spanish.

## How the database is read

With its **own read-only session**, separate from the open tabs. Only the
object list is mandatory: what the engine doesn't have or fails to read goes
to the notes.

## As a scheduled task step

The **Document the database** step of [`scheduled-tasks.md`](scheduled-tasks.md)
uses the same options as the dialog (format, schemas and parts). It writes to
a **Folder** with the **File name** you choose (it accepts
[variables](scheduled-tasks.md#variables)) and produces `file` and `tables`.

## Engine particularities

The document is built from what the engine reports through the contract, so
each engine comes out with what it has: without foreign keys there are no
links or lines in the diagram, and without dependencies there is no **Used
by**. What each engine lacks is in
[`engine-support.md`](engine-support.md#document-the-database).

## Contract

It uses the session methods `row_estimates` and `object_comments` (they
return empty by default) and those that already existed:
`Session::list_objects`, `database_schema` (tables, keys and indexes),
`columns` (what `database_schema` doesn't return, such as views),
`definition` (the code), `row_estimates` (approximate rows, from engine
statistics only), `object_comments` (comments of objects that are neither
tables nor columns), `server_version`, `list_schemas`, and the capabilities
`capabilities().foreign_keys` and `supports_dependencies()`.

Commands: `dbdocs_outline`, `dbdocs_generate` (event `dbdocs-progress`,
cancellable with `cancel_query` on `docs:<runId>`) and `dbdocs_open`. See
[`api-commands.md`](api-commands.md).
